简单来说，**静态代理**和**动态代理**是两种不同的实现代理模式的方式。而你提到的 **JDK 动态代理**和 **CGLib 动态代理**，则是实现动态代理的两种不同技术手段。

### 🏛️ 静态代理 vs. 动态代理

你可以把“代理”想象成一个中介。比如你想租房（目标对象），但你找了中介（代理对象）来帮你处理看房、签合同等一系列事情。

#### 静态代理

- **工作方式**：在程序编译阶段，代理类（中介）的 `.java` 文件就已经写好了，并被编译成了 `.class` 文件。一个代理类通常只为一个特定的接口或类服务。
- **优点**：结构清晰，容易理解。
- **缺点**：代码冗余。如果有很多个接口需要代理，就需要编写大量的代理类，非常繁琐。

#### 动态代理

- **工作方式**：在程序编译阶段，**并没有**现成的代理类。代理类是在程序**运行时**，由 JVM 根据一些规则动态生成到内存中的。
- **优点**：非常灵活，一个动态代理类可以代理多种不同类型的接口或类，大大减少了代码量。Spring AOP 就是基于动态代理实现的。
- **缺点**：理解起来稍微复杂一些。

### ⚙️ 两种动态代理的区别：JDK vs. CGLib

既然动态代理是在运行时生成代理类，那具体怎么生成呢？这就引出了两种主流的技术实现。

#### JDK 动态代理

- **核心原理**：利用 Java 的反射 API，特别是 `java.lang.reflect.Proxy` 类。
- **实现方式**：它通过实现**接口**的方式来创建代理。也就是说，被代理的类必须实现了至少一个接口，JDK 动态代理会生成一个该接口的实现类作为代理对象。
- **限制**：只能为实现了接口的类创建代理。

#### CGLib 动态代理

- **核心原理**：CGLib (Code Generation Library) 是一个强大的第三方代码生成库。
- **实现方式**：它通过**继承**的方式来创建代理。它会在运行时动态生成一个被代理类的子类，并拦截所有父类方法的调用，从而实现增强。
- **优势**：可以为没有实现任何接口的类创建代理。

### 总结对比

为了让你更清晰地理解，这里用一个表格来总结它们的区别：

|对比维度|JDK 动态代理|CGLib 动态代理|
|:--|:--|:--|
|**实现机制**|实现接口 (Implements Interface)|继承类 (Extends Class)|
|**使用限制**|目标类必须实现接口|目标类不能是 `final` 的|
|**性能**|生成代理类速度快，但执行时反射调用稍慢|生成代理类速度较慢，但执行时性能稍高|
|**Spring 选择策略**|默认首选，如果目标对象实现了接口，就使用它|如果目标对象没有实现接口，则自动使用 CGLib|

总而言之，Spring AOP 就像一个智能的决策者，它会根据你的目标对象是否有接口，自动选择最合适的动态代理方式（JDK 或 CGLib）来为你生成代理对象，从而实现对方法的动态增强。



## 什么叫“通过动态创建接口的实现类”来实现代理对象？


这句话听起来确实有点抽象，其实你可以把它想象成 Spring 在程序运行时，为你临时写了一个新的 Java 文件并立刻编译使用。

为了让你彻底明白，我们用一个通俗的例子来拆解这个过程。

### 🎬 场景设定

假设你有一个接口 `UserService` 和它的实现类 `UserServiceImpl`：

```java
// 接口
public interface UserService {
    void addUser();
}

// 真实的实现类
public class UserServiceImpl implements UserService {
    public void addUser() {
        System.out.println("保存用户数据...");
    }
}
```

现在，你想在 `addUser` 方法执行前后加上“开启事务”和“提交事务”的功能（这就是 AOP 增强）。

### 🧠 所谓“动态创建接口的实现类”

如果不使用动态代理，你可能需要手动写一个静态代理类来实现 `UserService` 接口，并在里面调用 `UserServiceImpl`。

而 **JDK 动态代理** 做的事情是：**它不需要你写这个文件，它在内存里帮你“写”了一个！**

Spring 在运行时，会在内存中动态生成一个类似这样的类（我们叫它 `$Proxy0`）：

```java
// 这是 Spring 在内存中动态生成的伪代码
// 注意：它实现了 UserService 接口
public class $Proxy0 implements UserService {

    // 它持有一个真正的对象（UserServiceImpl）
    private UserService target; 

    public $Proxy0(UserService target) {
        this.target = target;
    }

    // 它实现了接口中的 addUser 方法
    public void addUser() {
        // --- 增强逻辑（AOP 的前置通知） ---
        System.out.println("开启事务...");

        // --- 调用真实对象的方法 ---
        target.addUser(); 

        // --- 增强逻辑（AOP 的后置通知） ---
        System.out.println("提交事务...");
    }
}
```

### 🚀 这个过程是怎么发生的？

1. **你请求对象**：当你从 Spring 容器获取 `userService` 时。
2. **Spring 判断**：Spring 发现 `UserServiceImpl` 实现了 `UserService` 接口，且需要 AOP 增强。
3. **动态生成**：Spring 利用 JDK 的 `Proxy` 类，在内存中“无中生有”地造出了上面那个 `$Proxy0` 类。
4. **返回代理**：Spring 把这个 `$Proxy0` 的实例（对象）返回给你。

### 🤔 结果是什么？

- 你以为你拿到的是 `UserServiceImpl`。
- 实际上你拿到的是 `$Proxy0`（代理对象）。
- 当你调用 `addUser()` 时，实际上是调用的 `$Proxy0` 里的 `addUser()`，它先做事务处理，再调用真实的 `UserServiceImpl`。

### 📌 总结

**“动态创建接口的实现类”** 的意思就是：

**Spring 并没有修改你原本的代码，而是在内存中临时生成了一个“披着接口外衣”的新类。这个新类里塞进了你想要的增强逻辑（如事务、日志），并把原本的业务逻辑包裹在中间。**

这就是为什么 JDK 动态代理**必须要求目标类实现接口**——因为它生成的那个临时类，必须 `implements` 那个接口，才能“冒充”原本的对象。
