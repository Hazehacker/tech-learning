# 单线程

命令执行始终保持单线程（保证原子性和高效）







# 非阻塞I/O多路复用机制



Redis 的高性能网络模型核心： **“非阻塞 Socket + IO 多路复用 + 事件驱动”** 的协同设计（经典单线程模型）

### 核心机制拆解

1. **Socket 设置为非阻塞模式**  

   - 通过 `fcntl(fd, F_SETFL, O_NONBLOCK)` 设置所有客户端/监听 Socket 为非阻塞。
   - **作用**：`read`/`write` 时若内核缓冲区无数据/满，立即返回 `EAGAIN` 错误，**避免线程阻塞**，保障单线程持续处理其他事件。

2. **IO 多路复用（I/O Multiplexing）**  

   - **目的**：**单线程高效监控成千上万个 Socket 的就绪状态**（可读/可写）

   - 系统调用选择

     （`ae.c` 封装）：

     - Linux：`epoll`（默认，O(1) 复杂度，支持海量连接）
     - BSD/macOS：`kqueue`
     - 其他：`select`/`poll`（兼容性兜底）

   - **触发模式**：Redis 使用 **水平触发（LT）**（未设置 `EPOLLET`），事件未处理完会持续通知，逻辑更简单可靠。

3. **事件驱动循环（Reactor 模式）**  

   ```c
   while (1) {
       // 1. 阻塞等待事件（超时可处理定时任务）
       numevents = aeApiPoll(eventLoop, timeout); 
       
       // 2. 遍历就绪事件
       for (i = 0; i < numevents; i++) {
           // 3. 调用预注册的事件处理器
           processEvent(eventLoop, events[i]); 
       }
   }
   ```

   - 关键事件处理器：
     - 监听 Socket 可读 → `acceptTcpHandler`（接受新连接，设为非阻塞并注册读事件）
     - 客户端 Socket 可读 → `readQueryFromClient`（读取命令，解析后执行）
     - 客户端 Socket 可写 → `sendReplyToClient`（发送响应，未发完则保留写事件）





### 为何需要“非阻塞 + 多路复用”组合？

| 方案                  | 问题                       | Redis 方案优势               |
| --------------------- | -------------------------- | ---------------------------- |
| 阻塞 IO + 多线程      | 线程开销大、上下文切换频繁 | 单线程资源消耗极低           |
| 非阻塞 IO + 轮询      | CPU 空转（busy-waiting）   | 内核通知就绪事件，零轮询开销 |
| **非阻塞 + 多路复用** | —                          | **高并发、低延迟、高吞吐**   |

> **关键澄清**：  
>
> - IO 多路复用（如 `epoll`）**本身是同步 IO**（需应用主动 `read`/`write`），与异步 IO（AIO）有本质区别。  
> - “非阻塞”指 Socket 行为，“多路复用”指事件监控机制——二者缺一不可。



### 注意事项与演进

- **单线程瓶颈**：慢查询（如 `KEYS *`、大 Key 操作）会阻塞整个事件循环，需通过 `SLOWLOG` 监控优
- **Redis 6.0+ 多线程 IO**：
  网络读写（`read`/`write`）交由多线程处理（仍基于 epoll），**命令执行仍为单线程**，兼顾吞吐与数据一致性。可通过 `io-threads` 配置启用。
- **为何不全程异步？**
  Redis 核心设计哲学：**简单性 > 极致性能**。单线程避免锁竞争、保证命令原子性，多路复用已满足绝大多数场景需求。



### 举个实际流程

1. 客户端发送请求 → 内核将数据写入 Socket 接收缓冲区  
2. `epoll_wait` 返回“可读”事件 → 事件循环调用 `readQueryFromClient`  
3. 非阻塞 `read` 一次性读取所有数据（若缓冲区空则下次循环再试）  
4. 执行命令 → 结果写入输出缓冲区 → 注册“可写”事件  
5. 下次 `epoll_wait` 检测到可写 → `sendReplyToClient` 发送响应（缓冲区满则等待下次事件）



这种设计使 Redis 单线程轻松支撑 **10w+ QPS**，成为高性能内存数据库的基石。理解其原理，对优化客户端连接、排查网络延迟问题至关重要。





# 网络I/O场景的多线程

> Redis 6.0+ 引入
>
> 解决Redis在 网络IO上的瓶颈

| 项目     | 说明                                                         |
| -------- | ------------------------------------------------------------ |
| 作用范围 | 仅**加速 客户端数据的读取（read）与响应写入（write）**，<u>不涉及命令解析与执行</u> |
| 工作流程 | 1. 主线程接收连接（accept） <br />2. **将 socket 分配给 I/O 线程池批量读取请求数据** → 填入 client 缓冲区 <br />3. 主线程串行执行所有命令（关键！保证原子性） <br />4. 主线程生成响应后，**交由 I/O 线程池批量写回客户端** |
| 配置参数 | `io-threads 4`（建议 ≤ CPU 核心数） `io-threads-do-reads yes`（默认启用读多线程，写多线程需显式开启） |
| 价值     | 高并发场景下吞吐量提升 2–3 倍（尤其万兆网卡+多核 CPU），**避免网络收发成为瓶颈** |
| 注意     | I/O 线程仅做内存拷贝（memcpy），不解析协议、不执行命令；线程间无锁竞争 |













# 磁盘I/O场景的多线程

| 机制                 | 用途                                          | 实现方式                                                     | 与主线程关系                                                 |
| -------------------- | --------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 子进程（fork）       | RDB 快照、AOF 重写                            | `fork()` 创建子进程写临时文件（利用写时复制 COW）            | **主线程几乎不阻塞**（仅 fork 瞬间有停顿）                   |
| 后台 I/O 线程（BIO） | **AOF 刷盘（fsync）、关闭文件、惰性内存释放** | 固定 3 个独立线程（`bio_aof_fsync`/`bio_close_file`/`bio_lazy_free`） | 完全异步：主线程提交任务后立即返回，避免等待慢速磁盘操作（如 fsync 耗时数百 ms） |

> **澄清**：
>
> - BIO 线程 ≠ 网络 I/O 线程池（二者独立存在）
> - `appendfsync everysec` 时，fsync 由 BIO 线程在后台执行，主线程仅追加到缓冲区
> - 持久化写磁盘由**子进程**完成，非多线程（避免主线程阻塞）

```
客户端请求
    ↓
[网络 I/O 线程池] ←→ 读取请求数据 / 写入响应（Redis 6.0+）
    ↓
[主线程] → 命令解析 → **串行执行所有命令** → 生成响应 → 提交 BIO 任务
    ↓
[BIO 后台线程] → 异步 fsync / 关闭文件 / 释放内存
    ↓
[子进程] → RDB/AOF 重写（fork 后独立写磁盘）
```
