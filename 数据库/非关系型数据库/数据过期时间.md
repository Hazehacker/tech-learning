| 数据类型           | 推荐策略                   |
| -------------- | ---------------------- |
| 几乎不变的静态数据（如配置） | ✅ 不设过期时间 + 异步更新        |
| 热点数据（可预知）      | ✅ 预热 + 设置较长 TTL + 定期刷新 |
| 动态变化数据（如订单）    | ⚠️ 设置合理 TTL 或使用主动更新    |
| 临时数据（如验证码）     | ❌ 必须设短 TTL             |
| 所有数据           | ❌ 绝对不要全部不设过期时间         |



# 设置过期时间

**为什么需要设置过期时间？**

> **如果所有数据都不设置过期时间，会出现哪些问题？**

1. **内存泄漏 / 内存持续增长**
   - 缓存没有过期机制，**数据会越积越多**。
   - 即使**某些数据已经失效或不再使用，仍然占用内存**
   - 最终导致缓存服务（如 Redis）内存耗尽，引发 OOM（Out of Memory），甚至崩溃。
2. **缓存污染**
   - **<u>旧的、无效的</u>**数据长期存在，**影响缓存命中率**
   - 查询结果可能返回错误或过时的信息，除非你手动保证更新同步。
3. **无法应对数据变更**
   - 如果源数据变了，但缓存没更新（因为无过期），就会出现“脏读”。
   - 必须依赖外部机制（如消息队列、事件监听）来主动刷新缓存，否则容易出错。
4. **运维困难**
   - 无法通过 TTL 自动清理历史数据。
   - 清理和监控变得复杂，必须依赖人工干预或复杂的调度系统。
5. **缺乏容灾能力**
   - 比如数据库宕机恢复后，缓存中的旧数据仍保留，可能<u>与真实数据不一致</u>
   - 若没有定期校验或重建机制，风险很高。
6. **扩展性差**
   - 在分布式环境下，多个节点共享缓存，若全靠手动更新，一致性难以保障。
   - 而基于 TTL 的自动过期是**一种简单有效的“兜底”策略**
   
     > ==在极端/特殊情况下出现 缓存与数据库不一致时，过期策略能实现兜底==



















# 不设置过期时间

> 应对缓存雪崩的一种策略，只适用于特定类型的数据

适用场景：

- 几乎不变的配置信息（如系统参数、菜单结构）
- 缓存命中率极高且很少变更的热点数据
- 数据变更由业务主动触发（如管理员修改后通知缓存刷新）

不适用场景：

- **经常变动的数据**（如用户订单状态、商品库存、实时排行榜）

  > 对于经常变动的数据，如果不设置过期时间，容易造成数据不一致问题

- **有明确时效性要求的数据**（如促销活动、限时优惠）

  > 如果不设置过期时间，容易造成数据不一致问题

- **需要自动清理的临时数据**（如验证码、登录态 token）



**对于那些几乎不变化的数据不设置过期时间，通过异步方式删除/更新缓存**，更新的时候异步删除/更新缓存
